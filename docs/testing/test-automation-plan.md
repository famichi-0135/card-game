# 対戦ゲームのテスト自動化計画

## 目的

対戦結果、公開情報、再接続時の表示状態を壊す回帰を、ゲームエンジン、Durable Object、ブラウザの順に検出する。本計画は既存のゲームルールおよび通信契約を変更せず、その振る舞いをテストで固定する。

## 確定した設計判断

| 項目                      | 採用する仕様                                                                                                                                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 古い `clientStateVersion` | `clientStateVersion <= stateVersion` であれば、最新のサーバー状態に対してフェーズ、カード位置、対象、みなもとを再検証する。古いことだけでは拒否しない。                                                      |
| コマンド冪等性            | 同じ認証済みプレイヤーが同じ `commandId` と完全に同じ本文を再送した場合、受理・ルール上の拒否を問わず最初の結果を返す。別プレイヤーまたは異なる本文は `COMMAND_ID_CONFLICT` とし、保存済みビューを返さない。 |
| 切断敗北                  | `GameSession` の Alarm 実行時点の WebSocket 接続状況から切断プレイヤーを決め、ゲームエンジンの `HANDLE_DISCONNECT_TIMEOUT` で勝敗を確定する。                                                                |

上記は、[クライアント・サーバー通信境界](../backend/client-server-protocol.md)および[ゲームエンジン仕様書](../game/gameEngine-definition.md)を正とする。新しいテストは、この契約を変更する提案ではない。

## 対象としないこと

- クライアントによる楽観的なゲーム状態更新
- WebSocket をゲームコマンド送信経路にすること
- カードルール、勝敗規則、切断敗北規則そのものの変更
- 本番 D1 へテスト用ユーザーやセッションを書き込むこと

## 実装順序

各項目で、まず受け入れ条件を表すテストを追加する。既に実装済みの契約を固定するテストは、追加時点で成功してよい。未実装または不具合再現のテストは失敗を確認してから最小実装を行う。

### P0: 現行契約の回帰防止

| 領域                 | 受け入れ条件                                                                                                                                                  | テスト層                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| 古いクライアント状態 | 同じフェーズ内で別の合法操作が先行しても、古い `clientStateVersion` の操作を最新状態で再検証して受理する。未来のバージョンと古い `phaseSequence` は拒否する。 | ゲームエンジン単体      |
| 拒否コマンドの再送   | 最初は操作権がなく拒否されたコマンドが、その後に合法になっても、同じ `commandId` の再送は最初の拒否結果を返し状態を変えない。                                 | `GameSession` 統合      |
| Alarm と切断判定     | Alarm 時点で操作担当者だけが未接続なら相手を勝者にする。両者未接続なら引き分けにする。                                                                        | `GameSession` 統合      |
| 情報秘匿             | スナップショット、コマンド応答、イベント、WebSocket 通知、競合エラーに相手の手札、山札順、乱数 seed、内部効果設定を含めない。                                 | エンジン・HTTP・DO 統合 |

このPRでは、最初の3項目を実装する。情報秘匿の体系テストは既存の `player-view`、カードカタログ、ゲームAPI試験を整理した次のPRで追加する。

### P1: 状態遷移・競合・永続化

- [ ] 配置、連鎖、破棄、サポート、フェーズ終了について、同一カードの連続操作、古いフェーズ、期限境界、みなもと不足、固定5枠を検証する。
- [x] 同一対戦への並行リクエストを `Promise.all` で送信し、同じ操作の再送は一度だけ状態を進め、異なる操作は一つの直列順序（受理1件・古いフェーズの拒否1件）として確定することを検証する。
- [x] Alarm と通常コマンドが期限で競合したときは、Durable Object 内で先に直列化された操作だけが状態を確定することを検証する。期限ちょうどの通常コマンドは、先行するAlarmがなければ仕様どおり受理対象とする。
- [x] DO を eviction した後も、保存済みの受理結果・拒否結果、イベント連番、バージョン固定済みのカードカタログを復元できることを検証する。
- [x] `afterSequence` の差分取得について、連続、重複、欠落、最新値より大きい値を検証する。

### P2: フロントエンド同期とアクセシビリティ

- HTTP 応答前にカード・みなもと・フェーズを確定表示しない。受理応答の `PlayerGameView` だけを正本として表示する。
- 遅れて返ったスナップショットや連続する `GAME_UPDATED` 通知が、新しい状態を古い状態で上書きしない。
- 通信失敗時は同一 `commandId`・同一本文を再送し、拒否結果は利用者向けメッセージと再同期導線を表示する。
- キーボードだけでカード操作、対象選択、フェーズ終了、ダイアログの取消を行える。`prefers-reduced-motion`、フォーカス表示、色以外の識別情報を確認する。

### P3: ブラウザE2E

Playwright は、P0からP2の高速な単体・Workers統合試験を安定させてから導入する。導入時は次を前提にする。

- フロントエンドとバックエンドの起動コマンド、ポート、API接続先、テストDBを専用構成で固定する。
- 認証は、本番Bindingに存在しないローカルE2E専用の境界を利用する。実際の Better Auth セッション形式を経由し、本番D1・staging D1を使わない。
- 二つの独立した `BrowserContext` で、招待、参加、配置、サポート、再接続、勝敗確定を検証する。
- フィクスチャ盤面は表示・D&D・アクセシビリティの高速試験にだけ使い、重要なゲームルールと認可は完全統合E2Eで確認する。

## テスト設計の原則

- Durable Object の Alarm は `runDurableObjectAlarm()` で同期実行し、実時間待機をテストに入れない。
- 各テストは固有のゲームID・ユーザーIDを使い、前のテストの保存状態へ依存しない。
- 非公開情報の検証では、公開され得るカード定義IDではなく、相手だけが知るカードインスタンスID、山札順、seed、内部効果フィールドを確認する。
- E2Eでネットワークを操作する場合も、最終状態は HTTP スナップショットで検証し、WebSocket通知だけを正本にしない。

## 検証コマンド

```bash
pnpm --filter @disastar/game-engine run test
pnpm --filter @disastar/backend run test
pnpm --filter @disastar/game-engine run check-types
pnpm --filter @disastar/backend run check-types
pnpm --filter @disastar/game-engine run lint
pnpm --filter @disastar/backend run lint
```

P3の導入後に、別途 `pnpm run test:e2e` を追加する。
