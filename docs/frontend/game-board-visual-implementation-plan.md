# 対戦画面ビジュアル実装計画

## 1. 目的

直近の対戦画面モック（1536 x 1024）を視覚目標とし、既存のゲーム操作、公開情報境界、通信方式を変更せずに、`/games/:gameId`を情報密度の高いデスクトップ対戦盤へ更新する。

本計画では、モックと現行契約に差がある場合は現行の`PlayerGameView`、`PublicCardCatalog`、`AvailableGameActions`、公開イベント契約を優先する。表示用データが存在しない項目は推測や固定値で補わず、契約が追加されるまで表示しない。

## 2. 変更しない範囲

- `PlayerGameView`を確定表示状態の正本とする。
- ゲームコマンド、合法手判定、D&D、キーボード代替操作、再同期、エラー表示の意味を変えない。
- 相手の手札内容、山札内容・順序、内部効果設定を取得またはDOMへ出力しない。
- カード配置、連鎖、破棄では確認を挟まず、フェーズ終了と対戦中止だけ確認する。
- モバイル用対戦レイアウトは追加しない。最小表示領域は`1180 x 720`を維持する。
- カード画像の有無をゲームルールや操作可否の判定に使用しない。

## 3. モックとの差分方針

| モック上の情報     | 現行契約                         | 初回実装                                                 |
| ------------------ | -------------------------------- | -------------------------------------------------------- |
| 最大ラウンド数     | `PlayerGameView`に存在しない     | 現在ラウンドだけ表示する                                 |
| プレイヤー表示名   | `PlayerGameView`に存在しない     | `自分`、`相手`と陣営名だけ表示する                       |
| 公開イベント時刻   | 表示用イベント項目に存在しない   | 時刻を表示せず、順序と本文だけ表示する                   |
| HP                 | 現行ルールは`stamina`            | `STAMINA`として表示する                                  |
| カード画像         | `imageAssetId`は`null`を許容する | IDがある場合はR2画像、ない場合は属性別の仮画像を表示する |
| 人物画像・盤面背景 | 状態契約に存在しない             | UIアセットとして後工程で差し込む                         |

## 4. レイアウト設計

基準キャンバスは`1536 x 1024`とし、次の比率で再現する。狭い対応画面ではCSSカスタムプロパティで寸法を縮め、領域の順序と固定5枠は変えない。

```text
上部進行バー: 全幅、高さ 72〜84px

中央:
  左  180〜210px  相手・自分のステータス
  中  可変幅       相手・自分の攻撃グループ各5枠
  右  240〜292px  みなもと、公開イベント

下部:
  左〜中央列       捨て札、サポートゾーン、手札、山札
  右列             中央の情報サイドバーを継続
```

- 上部は`ROUND`、`PHASE`、操作主体、残り時間、最新イベント、接続状態、フェーズ終了、対戦メニューの順に並べる。
- 攻撃グループは上下とも5列を維持し、空き枠にもスロット番号を表示する。
- 自分側だけ合法な配置・連鎖対象を強調し、相手側は効果対象となる場合を除いて閲覧専用とする。
- 右サイドバーには双方のみなもと、相手の公開済み捨て札・サポート、公開イベント履歴を置く。ゲーム用語や操作ガイドは、みなもとの表示領域を圧迫しないようこの画面には追加しない。
- 相手のみなもとは二次情報としてコンパクトに表示し、自分のみなもとを主表示にする。相手の公開済みサポート・捨て札は、枚数と用途が判別できる独立ボタンとして相手パネル内に固定する。
- 公開イベント履歴はShadcn UIの`Accordion`で開閉する。閉じている間はヘッダーだけに留め、その高さを自分のみなもとへ再配分する。開いた場合だけ履歴領域が縦に拡大し、履歴の中だけをスクロールさせる。
- 下部のカードとゾーンは同じ高さ基準で揃え、手札の詳細は上方向へ開く。

## 5. UI部品

画像生成なしで先に作る部品は次のとおりとする。

- `GameProgressBar`: 区切りセル型の進行バー、接続状態、最新イベント、主要操作
- `PlayerSummary`: 陣営、スタミナ、手札枚数、山札枚数、接続・フェーズ状態
- `ManaPanel`: 陣営別属性名、総量、予約量、使用可能量
- `AttackGroupRow` / `AttackGroupSlot`: 固定5枠、カード連鎖、必要みなもと、現在攻撃力
- `BoardCard`: カード名、種別、属性、コスト、攻撃力、効果概要、画像受け皿
- `DiscardZone` / `SupportZone` / `DeckZone`: 枚数、ドロップ可否、詳細表示
- `PublicEventFeed`: Shadcn UIの`Accordion`配下で表示する公開イベント履歴。閉じた状態では最新本文だけをヘッダーへ表示する
- `CardArtwork`: `imageAssetId`を同一オリジンのR2配信URLへ変換し、欠損時は属性・陣営別の仮画像を描画する

アイコンは既存依存の`lucide-react`を使い、色だけに依存しないラベルとアクセシブルな名前を併記する。正式画像が必要な領域をCSS図形やSVGで代用しない。

## 6. R2アセット配信

### 6.1 バケットとBinding

| 環境       | バケット                       | Worker Binding |
| ---------- | ------------------------------ | -------------- |
| production | `disastar-game-assets`         | `GAME_ASSETS`  |
| staging    | `disastar-game-assets-staging` | `GAME_ASSETS`  |

R2バケットと`GAME_ASSETS` Bindingは作成済みとし、Frontend Workerが背景・カード画像を読み取り専用で配信する。アプリケーションからのアセット作成・更新は行わない。

Frontend Workerが`GET`と`HEAD`だけを`/game-assets/:key`で配信する。ブラウザへR2資格情報を渡さず、公開一覧、アップロード、削除APIは提供しない。

### 6.2 オブジェクトキー

```text
cards/<catalog-version>/<card-definition-id>.<content-hash>.webp
backgrounds/board/<asset-name>.<content-hash>.webp
portraits/<faction>/<asset-name>.<content-hash>.webp
ui/<asset-name>.<content-hash>.webp
```

- キーは不変とし、画像更新時はハッシュを変える。
- 許可する形式はAVIF、WebP、PNG、JPEGとする。SVGやHTMLは配信しない。
- 配信時はR2の`Content-Type`と`ETag`を引き継ぎ、`Cache-Control: public, max-age=31536000, immutable`と`X-Content-Type-Options: nosniff`を付ける。
- `imageAssetId`にはR2オブジェクトキーを保存し、Frontendが`/game-assets/`配下のURLへ変換する。
- 通常のローカルVite開発では、背景表示のために明示したリモート読み取り Binding を使う。E2E環境ではローカルR2を使い、いずれの環境でもアプリケーションからの書き込みは行わない。

### 6.3 アップロード例

```powershell
pnpm --filter @disastar/frontend exec wrangler r2 object put "disastar-game-assets/cards/<catalog-version>/<asset>.webp" --file "<local-file.webp>" --content-type "image/webp" --cache-control "public, max-age=31536000, immutable" --remote
```

画像のアップロードは開発者が明示的に実行し、アプリケーションからの書き込み機能は作らない。

## 7. 画像生成・差し込み仕様

利用者が生成する画像は、UI文字や数値を焼き込まず、次の表示領域だけを対象にする。

| 種類             | 推奨元画像                | 表示方法                                     |
| ---------------- | ------------------------- | -------------------------------------------- |
| カードアート     | 960 x 600、WebPまたはAVIF | カード上部へ`object-fit: cover`で表示        |
| 盤面背景         | 2048 x 1365以上、WebP     | 盤面全面へ表示し、可読性用のUI面を上に重ねる |
| 陣営ポートレート | 768 x 768、WebP           | ステータスパネル内へ表示                     |
| カード裏面       | 640 x 960、WebP           | 山札・非公開カード表示へ使用                 |

最初の画像差し込みでは、盤面背景1枚、カード裏面1枚、陣営ポートレート2枚、フィクスチャで表示されるカード7枚を優先する。全カード画像は同じ画角、彩度、夜間防災のアートディレクションで統一する。

## 8. 実装順序と受け入れ条件

1. 本計画とテストを追加し、未実装状態で失敗することを確認する。
2. R2 Binding、読み取り専用配信、URL変換を実装する。
3. 画像を必要としないUI部品を実装する。
4. 既存の`GameBoardView`と操作フックへ統合する。
5. `1180 x 720`、`1280 x 720`、`1440 x 900`、基準`1536 x 1024`で表示と主要操作を確認する。特に公開イベントの開閉で、閉じた状態は自分のみなもとが優先され、開いた状態は履歴が必要な高さだけを占有することを確認する。手札詳細はPortal経由で表示し、盤面の`clip-path`や重なり順に隠れないことを確認する。
6. 利用者が用意した画像をR2へ配置し、`imageAssetId`とUIアセット参照を設定する。

初回のコード完了条件は、既存契約テストと操作テストを維持し、R2画像がなくてもゲームを完了でき、画像があるカードだけ遅延読み込みで表示されることとする。
