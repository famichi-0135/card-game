# リファクタリングロードマップ

## 目的

この文書は、現行の利用者向け仕様を弱めずに、対戦処理の正しさ、障害復旧性、変更容易性を段階的に改善するための実施順を定める。各項目は原則として独立したPull Requestにし、観測可能な振る舞いを固定するテストを追加してから構造を変更する。

## 優先順位

### 1. 正しさと復旧性（今回実装）

次の項目は、機能追加より先に扱う。

- `GameSession`の状態保存後にカタログ保持またはAlarm同期だけが失敗しても、同一コマンド再送とAlarm再試行で冪等に復旧する。
- `CatalogArchive`への同一リース再主張では、保存済みアーカイブを再書き込みしない。
- カード種別の上限合計では合法なデッキを構成できないルール設定を拒否する。
- 永続状態では効果・イベントの次シーケンスを1以上とし、`status`と`phase`の不正な組み合わせを拒否する。
- フェーズ期限を過ぎた時点でクライアントの操作候補を再計算する。勝敗と状態遷移の最終判定は引き続きバックエンドの信頼済み時刻を正とする。

### 2. 操作と再同期

次のPull Requestでは、フロントエンドの操作状態を入力単位で明確にする。

- ドラッグ開始中またはキーボードで選択中のカードIDを操作状態の正本とする。
- ドロップ可能表示と実行可否を、そのカードに対する`AvailableGameActions`だけから導出する。
- イベント欠落後の再同期を状態機械として整理し、再同期開始前のイベント連番を完了扱いにしない。
- D&D、キーボード代替操作、期限到達、再同期競合をE2Eテストで固定する。

### 3. 待機部屋と保存量（今回実装）

バックエンドのライフサイクルと保存上限は、次の方針で確定した。

- `MatchLobby`から`GameSession.initialize`が明示的な失敗結果を返した場合は、元の期限と公開範囲を維持して`waiting`へ戻す。RPC例外で成否を判別できない場合は`starting`を保持し、同じ参加者による同一入力の再送だけを許可する。
- `starting`の作成者は取消、参加者は開始再試行を選べる。取消または30分の期限切れでは、先に`cancelled`を保存して新しい開始を止めてから`GameSession.abandon`を呼ぶ。応答だけ失われた初期化が実際には成功していても、セッションを参照不能にし、カタログリースを解放する。補償RPC失敗は30秒後のAlarmで再試行する。
- 公開部屋の`starting`は一覧から一時的に隠すが、再試行で`waiting`または`started`へ確定できるまでD1索引行を残す。`started`、`cancelled`、期限切れなどの終端状態だけを索引から削除する。
- 公開イベントは最新の連続範囲を最大1024件かつJSON換算512KiBまで保持する。`firstAvailableEventSequence`と`eventsComplete`で切詰めを通知し、保持外の演出をクライアントが諦めて正規状態へ復旧できるようにした。
- コマンド結果は状態本体と別のStorageキーへ保存し、受理結果192件、拒否結果128件、個別結果128KiBを上限とした。既存結果は24時間の再接続猶予中に削除せず、上限を超える新規結果は状態を確定する前に`COMMAND_RESULT_CAPACITY_REACHED`で拒否する。
- `CatalogArchive`は、初期化時にはフルカタログを登録して同一バージョンの内容を検証し、通常の再送・Alarm復旧では`gameId`、`CardCatalogVersion`、保持期限だけの`renewLease`を使う。対象バージョンが消失した場合だけフル登録へフォールバックする。外部同期完了マーカーは保存せず、軽量RPCを冪等に再主張する方針とした。
- カタログ保持、Alarm同期、対戦初期化、破棄補償の一部成功を再現する統合テストを追加した。

### 4. 大規模モジュールの分割

正しさを固定した後、責務単位に分割する。

- `execute-command.ts`: 共通検証、配置、サポート、タイムアウト、ラウンド解決をフェーズ別ハンドラーへ分ける。
- `game-session.ts`: RPC境界、永続化、外部インフラ同期、WebSocket配信、保存形式移行を分ける。
- `use-game-board-actions.ts`: 操作候補、コマンド生成、プレビュー状態、D&Dアダプターを分ける。

分割では公開型、エラーコード、イベント順序、状態遷移を変更しない。各分割前に既存の入出力を固定するcharacterization testを追加する。

### 5. 運用と配信性能

正しさの変更とは分け、計測可能な基準で改善する。

- 実装済み: 対戦、待機部屋、認証、学習、ルール、マイページをルート単位のdynamic importへ分割した。変更前は初期JavaScriptが831.28kB（gzip 255.45kB）だったが、変更後の初期entryは196.87kB（gzip 62.23kB）、初期entryと必須preloadの合計は約314.73kB、最大の遅延ルート`game-route`は266.54kB（gzip 79.35kB）となり、500kB超のVite警告を解消した。
- 継続基準: 初期エントリと必須preloadの合計を350kB以下、各生成チャンクを500kB未満に保つ。対戦専用のD&D、カードカタログ、Toastを他ルートの初期JavaScriptへ戻さない。`pnpm --filter @disastar/frontend run build`の出力を配信性能変更のPRで確認する。
- 未実装: Workerのdry-runは対象環境を明示し、複数環境を定義した`wrangler.jsonc`で誤った環境を選ぶ余地とビルド警告をなくす。
- 実装済み: `CatalogArchive.renewLease`を追加し、通常復旧でのフルカタログ転送と全量比較をなくした。初期登録と同一初期化入力の再送では、バージョン内容の競合を見逃さないため引き続きフル比較する。

## 判断が必要な事項

- 仕様書は将来の攻撃カード効果を`effects`で表現するとしている一方、現行の配置処理は効果を持つ攻撃カードを拒否する。効果実装を進めるか、当面の契約を効果なしへ限定するかを別途決める。

`MatchLobby`の開始失敗時の扱い、イベント・コマンド結果の保存上限、`CatalogArchive`の軽量更新方式、初期JavaScriptの分割基準は確定済みであり、判断待ちではない。

## Pull Requestの完了条件

- 対象の不具合または境界条件を再現するテストが、修正前に失敗し修正後に成功する。
- 公開契約、エラーコード、保存形式を変える場合は、互換性または移行方針を同じPull Requestへ記載する。
- `pnpm run format:check`、`pnpm run lint`、`pnpm run check-types`、`pnpm run test`、`pnpm run build`を実行する。
- 実行できなかった確認と残る判断事項をPull Request本文へ記載する。
